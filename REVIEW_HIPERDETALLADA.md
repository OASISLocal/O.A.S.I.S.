# Review hiperdetallada de la web O.A.S.I.S.

Fecha: 2026-09-20

## 1. Resumen ejecutivo

La web tiene una base muy sólida: personalidad visual clara, tono consistente, propuesta diferenciada y un posicionamiento que comunica bien la idea de “AI local para Windows”. El producto promete algo fuerte: un asistente que vive en tu PC, funciona sin depender de la nube, protege la privacidad y permite actuar sobre archivos, documentos y equipo local.

Sin embargo, en su estado actual la web se siente más como un documento técnico de producto que como una landing page de conversión y crecimiento. Tiene identidad y calidad, pero falla en varios puntos clave:

- la promesa principal no se entiende con rapidez
- hay demasiada densidad técnica antes de explicar el beneficio real
- el contenido de la home está muy cargado
- el pricing no está del todo defendido como oferta activa
- hay inconsistencias de nomenclatura y marca
- la web no aprovecha al máximo la prueba social, evidencia y casos de uso concretos
- la arquitectura de contenido es más artesanal que escalable

En otras palabras: la web tiene “buenas ideas bien expresadas”, pero no siempre una “fuerza de venta clara y directa”.

---

## 2. Qué funciona realmente bien

### 2.1. Identidad visual muy fuerte
La marca transmite una personalidad muy definida: minimalista, tech, monoespacio, local-first, premium-informal. El diseño es coherente, con un enfoque bastante original que distingue la web de muchas landing pages de IA.

Fortalezas:
- typography correcta y consistente
- uso de “look and feel” editoral / hardware
- paleta con carácter de producto local y técnico
- se percibe una identidad propia muy clara

Esto es una ventaja competitiva sólida. La marca no parece genérica ni “AI copycat”.

### 2.2. Propuesta diferenciada
La promesa de “AI que vive en tu PC” tiene mucha fuerza. Es una idea comprensible en una frase y muy diferenciable frente a asistentes basados en la nube.

La clave de valor es clara:
- privacidad
- control local
- no depender de un servidor externo para tareas normales
- actuar sobre el equipo local
- no exigir cuenta ni cloud para uso cotidiano

Eso es una promesa con relevancia real y un buen razón de compra para muchos usuarios.

### 2.3. Estructura seccionada bastante buena
La home está organizada por bloques temáticos:
- hero
- demo
- loop de agente
- posibilidades de uso
- control / permissions
- tools
- security
- models
- download
- pricing
- waitlist
- FAQ
- cierre

Esto ayuda a que el visitante pueda navegar la propuesta sin perderse. El sitio tiene una buena intención de explicar todo el producto en un flujo comprensible.

### 2.4. Hay una intención clara de conversión
La web quiere que el usuario descargue o se apunte a la waitlist. Eso está bien.

Hay CTA visibles y repetidos, con enlaces a release, waitlist y GitHub. La página no es pasiva: intenta mover al usuario a una acción.

---

## 3. Los puntos débiles más importantes

## 3.1. La home no transmite la promesa principal con rapidez
Este es probablemente el punto más serio.

La página intenta decirlo todo a la vez: local-first, memory, tools, permissions, security, models, pricing, waitlist, GitHub, roadmap, changelog, FAQ, etc. El problema es que un visitante nuevo no suele tener energía para procesar la totalidad del posicionamiento antes de entender qué hace el producto.

La frase principal del hero es buena, pero la página entera se complica demasiado rápido. La promesa central no se cristaliza con suficiente fuerza al inicio.

### Qué pasa exactamente
El usuario llega y tiene que interpretar varios niveles de significado:
- ¿Es un chatbot?
- ¿Es un asistente local?
- ¿Es un agente para controlar el PC?
- ¿Es un IDE o un copiloto para desarrolladores?
- ¿Es un producto para end users o usuarios técnicos?
- ¿Es gratis, beta, waitlist, o ya disponible?

Eso crea una ligera confusión. La narrativa no termina de “encajar” en una sola idea dominante.

### Impacto
- pérdida de claridad
- más tiempo para entender
- peor performance en conversión por parte de usuarios no técnicos
- baja comparación con la competencia que ofrece mensajes más simples

### Recomendación
Que la promesa central se convierta en una frase única, repetida varias veces, por ejemplo:

“O.A.S.I.S. es un asistente personal para Windows que trabaja con tus archivos, documentos y PC sin mandar tus datos a la nube.”

Luego añadir una segunda línea:

“Hazlo todo desde tu propio equipo: buscar archivos, resumir PDFs, recordar cosas, explicar código y controlar tareas locales con permiso.”

Eso haría que todo el resto del contenido se entendiera mejor.

---

## 3.2. Demasiada densidad técnica antes del beneficio real
El sitio está muy bien hecho para un usuario técnico. Pero el problema es que gran parte del contenido usa jargon sin ponerlo bien en contexto.

### Ejemplos de jargon que aparecen a menudo
- local-first
- semantic search
- tool servers
- MCP
- sandbox
- permissioned
- high-impact actions
- GGUF models
- VRAM
- Docker
- server
- localhost
- integration

Esto no es malo en sí mismo, pero está mal posicionado si el objetivo principal es convertir a un usuario general o incluso a un early adopter con poca paciencia.

### El problema real
La web va un poco por este camino:

“Explica la tecnología”
→ antes que
“explica el beneficio”

Eso hace que la página se lea más como página de documentación que como pieza de marketing.

### Impacto
- el value prop emocional no aparece tan fuerte
- el visitante no sabe exactamente qué cambia en su día a día
- se pierde la sensación de “esto me ahorra tiempo”

### Recomendación
Separar dos niveles de lectura:

1. Nivel 1: beneficio directo para todos
2. Nivel 2: detalle técnico para usuarios avanzados

La home debería priorizar nivel 1 casi por completo. Nivel 2 debe estar en páginas internas o detalladas, no arriba en la home.

---

## 3.3. Hay demasiadas secciones y demasiada información a la vez
La home tiene bastante contenido y visualmente está muy bien hecha, pero a veces se siente como una “página de catálogo completo” más que una página con foco.

### Ejemplos de sobrecarga
- multiple sections: demo, agent loop, tasks, control, tools, security, models, download, pricing, waitlist, FAQ, cierre
- demasiados conceptos en la parte superior del flujo
- se repite la idea de local-first, permissions, tools, workspaces, memory, etc.

Esto puede ser interesante para un usuario muy interesado, pero es pesado para alguien que entra a ver si el producto le sirve.

### Impacto
- más esfuerzo mental
- menos foco en la acción principal
- peor “narrativa de compra”
- la página se siente más larga que necesaria

### Recomendación
Que la home se divida en 3 capas:

1. Promesa principal + CTA
2. Demostración del producto en acción
3. Pruebas de valor / diferencias / confianza

Todo lo demás puede ir más abajo o en páginas específicas.

---

## 3.4. El pricing tiene potencial, pero no está defendido como oferta real
El pricing tiene un buen concepto: free Personal + one-time Max. Eso es una decisión muy buena.

Sin embargo, la ejecución de la oferta está menos fuerte de lo que debería.

### Qué está bien
- personal gratis
- Max one-time payment, no subscription
- la visión de modelo de negocio es clara
- la estructura por planes está ordenada

### Qué falla
- Max no está a la venta todavía
- la web anuncia una oferta que no puede cerrar
- no hay una sensación clara de disponibilidad real
- la expectativa de compra está parcialmente bloqueada

### Impacto
- el pricing parece más “plan conceptual” que “oferta activa”
- la conversión de la waitlist se vuelve más un trámite que una compra real
- a la larga puede generar sensación de “esto no está listo”

### Recomendación
- dejar muy claro si hoy mismo se vende o no
- distinguir “beta free”, “early access” y “on-sale” de forma muy visual
- si Max todavía no está disponible, enfatizar el “funding/early access” como una promoción, no como “precio final” con la sensación de compra inmediata

---

## 3.5. Hay inconsistencias de marca y nomenclatura
Este punto parece menor, pero es importante para credibilidad y pulido.

### Observado
El sitio alterna entre:
- O.A.S.I.S.
- OASIS
- O.A.S.I.S. / OASIS indistintamente
- “O.A.S.I.S. v0.2.0 beta”
- “OASIS” en algunos tags/descripciones
- nombre de producto y nombre de la organización no totalmente alineados

### Impacto
- la marca pierde coherencia
- el producto parece menos pulido
- la percepción de “seriedad” baja ligeramente

### Recomendación
Elegir una versión oficial de nombre y usarla siempre.

Ejemplo recomendado:

O.A.S.I.S.

Y usarlo siempre igual en:
- title
- meta descriptions
- OG tags
- headers
- menú
- footer
- CTA
- links
- changelog

No alternar con OASIS cuando la marca oficial es O.A.S.I.S.

---

## 3.6. Faltan señales de prueba social y evidencia concreta
La web tiene un buen diseño, pero no tiene bastante evidencia “real” de uso.

### Qué hay actualmente
- GitHub stars
- roadmap
- changelog
- waitlist
- promesas de privacy y seguridad

### Qué falta
- testimonios de usuarios
- ejemplos de tareas reales
- casos de uso concretos con resultados
- screenshots del producto mayormente usado
- micro stories de productividad real

### Impacto
El visitante puede quedar con la sensación de “esto parece bien en teoría, pero ¿qué hace la gente real?”

### Recomendación
Añadir una sección como:

“¿Qué hace la gente con O.A.S.I.S.?”

Con 3–5 ejemplos reales:
- “Busca facturas del último trimestre y calcula gastos”
- “Resume un PDF y crea un informe corto”
- “Lee archivos, busca la información correcta y te lo resume”
- “Explica un error en código sin abrir 20 pestañas”
- “Llama a un archivo, lo organiza y te deja un resumen estructurado”

O incluso mejor: añadir una mini experiencia “demo real” con pantallas o mockups en acción.

---

## 3.7. El sitio está muy bien diseñado como explainer, pero no tanto como sistema de crecimiento
La web claramente está pensada como pieza de marca y explicación. Eso está bien, pero no está pensada como un funnel intensivo de crecimiento.

### Qué falta para convertir mejor
- más claro “del problema al beneficio”
- más continuidad entre home, download y pricing
- más urgencia real de acción
- más pruebas de valor antes del CTA final
- más storytelling del “antes y después”

### Impacto
La web puede ser muy bonita, pero no siempre está optimizada para convertir a la gente que llega por curiosidad o por interés real.

### Recomendación
Cada página debería tener una intención clara:

- Home: educar y captar interés
- Download: convertir interés en instalación
- Pricing: diferenciar valor y preparar compra
- FAQ: quitar fricción final

La estructura actual es buena, pero a veces no está tan nítida como debería.

---

## 3.8. Hay una poca diferenciación entre “AI local”, “AI agent” y “AI assistant personal”
El sitio usa varios términos, y aunque todos son relacionados, no siempre están diferenciados con claridad.

### Diferencias que deberían quedar claras
- AI assistant personal
- AI agent that acts on your machine
- local-first system
- PC control assistant
- productivity assistant
- code assistant
- workflow automation

Cuando todas estas ideas aparecen sin una definición clara, el producto puede sonar un poco mixto.

### Impacto
- confusión conceptual
- menos claridad de posicionamiento
- más dificultad para explicar el diferencial real

### Recomendación
Definir una línea de posicionamiento de 2–3 frases y usarla consistentemente:

“Un asistente personal para Windows que trabaja con tus archivos, apps y PC, sin depender de la nube.”

Eso ayuda a unificar todo el discurso.

---

## 3.9. El diseño visual es muy bueno, pero a veces incrementa la carga cognitiva
La estética es muy marcada y eso aporta valor, pero también puede dificultar la lectura rápida.

### Ejemplos
- mucho uso de caja, líneas, caparazones, border, terminal-like blocks
- mucho visual “scholarly” o “boilerplate design”
- muchos elementos con texturas de sistema/terminal
- gran cantidad de detalles visuales en secciones largas

Esto está bien si el objetivo es atraer a un público técnico, pero si el sitio quiere atraer a más usuarios, este exceso de estilo puede volver la lectura más pesada.

### Impacto
- esfuerzo de lectura más alto
- más foco en estética que en claridad
- censurar un poco la capacidad de síntesis del producto

### Recomendación
Dejar la coherencia visual, pero reducir el número de elementos en el hero y las primeras secciones. Ordenar más claro: menos bloques, más espacio, más llamada a la acción, menos peso visual de fondo.

---

## 3.10. El sitio no aprovecha al máximo el “case study mini”
Un sitio como este necesita un poco de narrativa concreta. Aun en una landing page técnica, los ejemplos de tareas reales hacen mucho.

### Qué podría funcionar muy bien
- “Busca mis facturas del trimestre y resúmalas”
- “Clasifica mis documentos por tipo y encuentra esto en dos minutos”
- “Explica el error de esta app y sugiere arreglos”
- “Hazme un resumen de 5 archivos de trabajo”
- “Llama mis notas, calendario y documentos para preparar esta reunión”

Esto transforma la promesa abstracta en una acción tangible.

### Impacto
- mayor comprensión del producto
- mejor conversión
- más diferencia frente a una IA generalista

### Recomendación
Añadir al menos una sección con “tareas reales” y “output real”.

## 4. Problemas técnicos / de mantenimiento

## 4.1. Duplicación de CSS entre la home y la base compartida
La home en [index.html](index.html) tiene un bloque enorme de estilos inline, y además hay un CSS compartido en [assets/site.css](assets/site.css). Esto levanta varios problemas:

- la misma lógica visual está repetida
- se hace más difícil mantener consistencia
- se pueden producir inconsistencias entre páginas
- el CSS inline hace más difícil escalar el diseño

### Recomendación
Establecer una única fuente de diseño y una sola página base para estilos reutilizables. Mantener [assets/site.css](assets/site.css) como base y reducir el CSS inline en home a lo notablemente específico.

---

## 4.2. Duplicación de estructura y diseño entre páginas
Las páginas se sienten similares, pero no están diseñadas con un sistema compartido real. Esto ayuda al estilo, pero no al mantenimiento a largo plazo.

### Recomendación
Crear un sistema de componentes reutilizables:
- hero
- CTA row
- section header
- cards
- table specs
- FAQ
- closer section
- footer standard

Así el sitio crece sin romperse.

---

## 4.3. Marca y copy no siempre están alineadas con el producto real
Hay mucho contenido prometedor, pero la página no siempre comunica la línea de producto con total coherencia. Algunas secciones hablan de un producto mucho más grande o más avanzado que lo que se ve demostrado en la home.

### Impacto
- visita con expectativa alta
- luego sensación de “no es exactamente esto”
- pérdida de confianza

### Recomendación
Hacer que cada promesa del site esté respaldada por una demostración, un caso real o una frase muy clara de contexto.

---

## 5. Qué mejoraría la web en términos de experiencia de usuario

### 5.1. Mejorar el primer vistazo
Reducir el primer bloque a un “monólogo” de 3 ideas:
- lo que es
- lo que hace
- por qué importa

### 5.2. Mejorar la comprensión del valor
Mostrar 3 ejemplos concretos en la parte superior:
- buscar archivos y resumir facturas
- extraer partes de PDFs
- explicar error de código

### 5.3. Mejorar el “path to action”
Hacer más evidente:
- Download
- Install
- Download model
- Test with one prompt

### 5.4. Mejorar el “área de prueba social”
Añadir ejemplos reales, testimonios, ratios de uso a lo largo del sitio.

### 5.5. Mejorar la legibilidad del pricing
Resaltar la diferencia entre free y Max con una tabla muy limpia. Si no se vende ya, dejarlo como “early access” y dejar la compra real más abajo.

---

## 6. Qué haría yo primero si tuviera que arreglarlo

### Fase 1: claridad de producto
- reescribir el hero
- acortar el primer bloque de explicación
- dejar una única promesa principal
- simplificar el lenguaje del primer scroll

### Fase 2: optimización de conversión
- aumentar claridad de CTA
- cambiar la narrativa de “docs” a “beneficio / acción”
- reforzar ejemplos reales

### Fase 3: consistencia y mantenimiento
- unificar estilos
- reducir CSS duplicado
- crear una system base

### Fase 4: crecimiento y trust
- añadir testimonios
- añadir casos concretos
- añadir más señales de actividad real

---

## 7. Conclusión final

La web tiene mucha personalidad y una propuesta muy buena, pero en este momento funciona más como una “explicación técnica bien construida” que como una página de conversión realmente enfocada. La principal oportunidad de mejora no es estética sino de comprensión, prioritización y foco comercial.

La mejor versión de esta web tendría esta estructura:

- una promesa central muy clara
- un hero mucho más directo
- menos jargon en la parte de arriba
- más ejemplos reales de uso
- pricing más claro y más accionable
- menos ruido visual en la primera mitad del flujo
- más señales de confianza y evidencia real

Si esto se corrige, la web puede pasar de ser “muy buena” a ser “muy convierte”.

---

## 8. Resumen de puntos clave en un vistazo

### Lo que está bien
- marca fuerte
- identidad visual clara
- concepto local-first con potencial
- buen tono general
- estructura general razonable

### Lo que está peor
- demasiada densidad técnica de entrada
- falta de claridad comercial inmediata
- overloading de información en la home
- pricing no totalmente defendido
- inconsistencias de naming
- falta de prueba social / evidencia
- CSS y mantenimiento poco escalables

### Mejor prioridad de acción
1. Reescribir hero y promesa principal
2. Simplificar la home
3. Mejorar la claridad de pricing y waitlist
4. Añadir prueba social y ejemplos reales
5. Unificar marca y estilos
